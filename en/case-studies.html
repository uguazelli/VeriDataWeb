Technical Dilemmas & Solutions

A. The Serverless Latency Problem (Hono vs. NestJS)

Dilema: The initial spec proposed NestJS on AWS Lambda. While NestJS provides clean enterprise organization, its heavy dependency-injection container leads to cold start latencies of 1.5 to 3 seconds. For a real-time ERP interface, this lag ruins the user experience.

Decision: We replaced NestJS with Hono running on Node.js. Hono is a zero-dependency, ultra-lightweight framework built specifically for serverless edge/lambda environments.

Solution: Cold starts dropped to under 150ms, offering an instantaneous, smooth experience for clients approving budgets.

B. Rigid Identity vs. Dynamic Permissions (Cognito vs. DB-Level RBAC)

Dilemma: Managing complex multi-tenant client hierarchies and granular role-based permissions (RBAC) directly inside Cognito Groups is rigid, hard to audit, and bloats JWT token payloads.

Decision: We use Amazon Cognito strictly for Authentication (verifying identity). All Authorization (permissions logic) is managed entirely within PostgreSQL tables.

Solution: This keeps Cognito clean and secure. We can update client approval limits or vendor permissions instantly in DB tables without modifying Cognito schemas.

C. Database Connection Starvation (RDS Proxy)

Dilemma: PostgreSQL opens a separate OS process for every single connection. In a serverless architecture, Lambda functions scale horizontally. A sudden surge of vendors updating stock would spin up dozens of Lambda containers, instantly exhausting database connection limits.

Decision: We deployed Amazon RDS Proxy between the Lambda functions and the Aurora database.

Solution: RDS Proxy maintains a persistent connection pool, multiplexing connection requests from active Lambdas to keep database connection counts stable.

D. Cost Control for Autoscaling Databases (Aurora Serverless v2)

Dilemma: While Aurora Serverless v2 scales automatically based on capacity units (ACUs), inefficient queries or excessive client polling will trigger high capacity scaling, leading to unexpectedly high monthly AWS bills.

Decision: We set strict min/max limits on ACU scaling inside Terraform, and implemented React Query cache layers on the frontend.

Solution: The database safely scales down to its minimum capacity (0.5 ACUs) during off-hours, cutting database operational costs by over 60%.

E. Long-Running Workloads (Lambda SQS vs. Future ECS)

Dilemma: Generating 200+ page high-resolution catalogs or parsing massive Excel sheets can easily exceed AWS Lambda's strict 15-minute runtime execution limit.

Decision: We used an EventBridge router and SQS queue to process standard async tasks.

Solution: Decoupling the queue means that if import sizes grow, we can migrate the worker Lambdas to persistent AWS Fargate (ECS) containers in Phase 2 without rewriting any of the core API logic.

Technical Dilemmas & Solutions

A. Dynamic Multi-Tenant Routing

Dilemma: Managing separate n8n workflows for each tenant CRM would be a maintenance nightmare as client onboarding increases.

Decision: Built a single, parameterized workflow using dynamic lookups (GET: Tenant Settings) and a centralized SWITCH router node to direct payloads based on client CRM configurations.

Solution: A single n8n template workflow supports multiple CRMs (EspoCRM, HubSpot) and dozens of tenants simultaneously with zero maintenance overhead.

B. Race Conditions & Deduplication

Dilemma: Webhook spikes can trigger duplicate contacts in the CRM if multiple chat messages arrive from the same email before the first contact creation database operation completes.

Decision: Implemented a multi-stage validation check (Check if Lead Exists -> Check if Contact Exists on match).

Solution: Ensures the pipeline updates existing CRM records dynamically and keeps contact mapping tables clean, achieving 100% data integrity.

C. Stale ID Mapping Recovery

Dilemma: When a sales operator converts a lead into a contact in the CRM manually, old ID references in n8n's lookup table cause sync errors on future messages.

Decision: Added a verification branch (LeadCondition) that checks the CRM record state.

Solution: If a mapping reference is stale, n8n triggers the Delete old mapping endpoint automatically, clearing references and starting a clean sync flow on the next update.

MuleSoft 3-Tier Integration Case Study

Identity Resolution & Registry Integration for US Plasma Donors

A high-security, 3-tier API-led MuleSoft architecture orchestrating donor registration, verification, and medical deferral synchronization.

Architectural Blueprint

graph TD subgraph Experience Layer SFHC[Salesforce Health Cloud] MobileApp[Mobile App: DAPP] ExpAPI[Donor Mobile Experience API] SFHC --> ExpAPI MobileApp --> ExpAPI end subgraph Process Layer ProcAPI[Donor Process API] ExpAPI --> ProcAPI end subgraph System Layer SFHCSys[Salesforce Health Cloud System API] DMSSys[DMS Core Database System API] MobileSys[Mobile System API] EmailSys[External Provider Email SAPI] ProcAPI --> SFHCSys ProcAPI --> DMSSys ProcAPI --> MobileSys ProcAPI --> EmailSys end subgraph Data & Identity Engines SFHCSys --> SalesforceHC[(Salesforce Health Cloud Database)] DMSSys --> OracleDMS[(Oracle Database: Core Donor DMS)] OracleDMS --> Data360[Data360: Identity Resolution Engine] EmailSys --> AmazonSES[Amazon SES / Email System] end

Technical Dilemmas & Solutions

A. US Compliance & PII-Safe Identity Resolution

Dilemma: US regulations require verifying donor identity against national medical deferral registries to prevent ineligible donors. However, strict HIPAA and data security compliance prohibit storing full Social Security Numbers (SSN) within the Mobile App or intermediate integration layers.

Decision: Configured a secure identity resolution layer via the DMS System API and Data360. We query records using First Name, Last Name, Date of Birth (DOB), and *only* the last 4 or 5 digits of the SSN (processed and matched as one-way encrypted hashes).

Solution: Achieved 100% compliance alignment, preventing profile duplication and ensuring medical deferral records match correctly without compromising sensitive PII.

B. 3-Tier API-Led Connectivity Architecture

Dilemma: Creating direct peer-to-peer data pipes between Salesforce Health Cloud, the mobile app, and the legacy Oracle DMS database creates high dependency coupling, making schema updates risky and slowing down releases.

Decision: Deployed MuleSoft's 3-tier API architecture: Experience APIs (channel-optimized interfaces), Process APIs (business logic orchestration), and System APIs (secure database adapters).

Solution: Fully decoupled backend systems. We can optimize or upgrade the Oracle DB schema underneath `dms-sys-api` without impacting mobile app operations.

C. Event-Driven Deferral Auditing & Marketing Blockers

Dilemma: If a donor is deferred due to a medical exam at a physical donation center, promotional emails/SMS must stop immediately. Synchronizing this status via daily batch runs leaves a compliance window open, exposing the company to audit penalties.

Decision: Implemented a real-time `Event Listener` system API. When a deferral is recorded in the Oracle DMS database, it fires an immediate message queue event, which the Process API routes to update Salesforce Health Cloud and Marketing Cloud.

Solution: Promotional messaging is suspended in under 1 second of deferral registration, eliminating compliance gaps.
